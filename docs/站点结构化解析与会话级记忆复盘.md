# 站点结构化解析与会话级记忆复盘

## 1. 这项改造解决了什么问题

SolarAgent 早期只把用户输入的站点简称当作普通文本传递，例如：

```text
用户：预测哲丰今天的发电量
Agent：哲丰匹配到多个站点，请选择
用户：2（哲丰新材料九号机）
```

旧链路的问题是：后续预测、天气、图表工具可能再次拿原始文本“哲丰”去查库。
由于“哲丰”仍然对应多个站点，系统会重复询问用户，或者不同工具选择出不同站点。

本次改造的核心不是让大模型“记住一句话”，而是把用户确认后的站点转换成稳定的业务对象：

```text
模糊站点文本
    → 站点解析
    → 结构化站点对象
    → 当前任务内复用
    → 任务成功后保存为会话级 active_station
    → 下一轮通过“它/刚才那个站点”继续复用
```

最终解决了两个层次的问题：

| 问题 | 解决方式 |
| --- | --- |
| 同一次任务中反复询问站点 | `StationResolutionContext` + `ContextVar` |
| 下一轮对话忘记用户刚才选的站点 | `chat_session.context_json` + `active_station` |
| “宁波地区全部站点”被误判为单站点歧义 | `single / multi / region` 范围解析 |

## 2. 当前版本的总体架构

```text
                         ┌──────────────────────────────┐
                         │        用户自然语言输入        │
                         └──────────────┬───────────────┘
                                        │
                                        ▼
                         ┌──────────────────────────────┐
                         │      Agent 判断站点范围        │
                         │ single / multi / region      │
                         └───────┬──────────┬─────────────┘
                                 │          │
                    单站点/多站点 │          │ 地区站点
                                 ▼          ▼
                    ┌───────────────┐  ┌──────────────────┐
                    │ StationResolver│  │ get_stations_    │
                    │ 解析单个实体   │  │ by_region        │
                    └──────┬────────┘  └────────┬─────────┘
                           │                    │
                           ▼                    ▼
                    ┌────────────────────────────────────┐
                    │      结构化站点对象 / 站点列表       │
                    │ id、标准名称、经纬度、容量、地区信息 │
                    └────────────────┬───────────────────┘
                                     │
                 ┌───────────────────┼────────────────────┐
                 ▼                   ▼                    ▼
          实际发电量查询          天气查询              发电量预测
                 │                   │                    │
                 └───────────────────┼────────────────────┘
                                     ▼
                          图表 / 导出 / 分析结果
```

这条链路没有引入新的 TaskPlan 或复杂执行器。站点解析只负责确定“本次要操作哪些站点”，下游业务继续复用原来的查询、预测和图表代码。

## 3. 改造过程：从重复匹配到结构化复用

### 3.1 第一阶段：工具各自进行模糊匹配

早期每个工具可能有类似逻辑：

```text
用户输入“哲丰”
    ├─ 天气工具自己匹配
    ├─ 预测工具自己匹配
    ├─ 发电量工具自己匹配
    └─ 图表工具自己匹配
```

这会导致：

1. 相同站点匹配逻辑分散在多个文件；
2. 用户选择结果无法传给下一个工具；
3. 每个工具可能重复访问数据库；
4. 同一个简称在不同工具中可能得到不同站点。

### 3.2 第二阶段：引入共享 `StationResolver`

现在统一入口位于：

```text
backend/app/services/station_resolver.py
```

核心入口：

```python
resolve_station(station_name)
```

它统一负责：

```text
规范化用户输入
    ↓
读取站点数据
    ↓
模糊匹配全部候选
    ↓
唯一匹配：直接返回
多匹配：ask_user 询问
无匹配：返回 None
    ↓
保存本次解析结果
```

这一步完成了职责收口：业务工具不再自行实现一套站点匹配逻辑。

### 3.3 第三阶段：返回结构化站点对象

站点解析成功后，返回的不是一句文本，而是一个 Python `dict`：

```python
{
    "station_id": "4",
    "name": "哲丰新材料九号机新增",
    "province": "浙江省",
    "city": "衢州市",
    "location": "浙江省衢州市常山县辉埠镇...",
    "lat": 28.941447,
    "lon": 118.525745,
    "capacity_kw": 300.0,
}
```

预测工具随后使用结构化字段：

```python
station_info = resolve_station(station_name, stations=stations)

station_id = station_info["station_id"]
full_name = station_info["name"]
lat = station_info["lat"]
lon = station_info["lon"]

predict_station_power(
    station_id=station_id,
    station_name=full_name,
    lat=lat,
    lon=lon,
    predict_date=predict_date,
)
```

注意：预测底层接收的是 `station_id`、标准名称和经纬度，不再继续传递模糊文本“哲丰”。

### 3.4 第四阶段：增加任务级 `ContextVar`

在一次 Agent 执行开始时，`chat.py` 创建独立上下文：

```python
station_context_token = bind_station_resolution_context(
    active_station=active_station,
)
```

上下文中主要有三个字段：

```python
@dataclass
class StationResolutionContext:
    resolved_by_alias: dict[str, dict[str, Any]]
    active_station: dict[str, Any] | None
    last_user_selected_station: dict[str, Any] | None
```

其中：

- `resolved_by_alias`：当前任务已经解析过的别名映射；
- `active_station`：从上一轮会话加载的站点提示；
- `last_user_selected_station`：本次任务中用户刚刚确认的站点。

用户第一次选择九号机后，当前任务中会形成：

```text
“哲丰”                       ┐
“4”                           ├──> 同一个结构化站点对象
“哲丰新材料九号机新增”         ┘
```

所以后续工具即使传入“哲丰”、站点 ID 或完整名称，也会得到同一个站点。

### 3.5 第五阶段：增加会话级 `active_station`

任务级 `ContextVar` 只能存活到本次 Agent 执行结束。为了支持下一轮对话，新增：

```sql
ALTER TABLE chat_session
ADD COLUMN context_json JSON NULL;
```

迁移文件：

```text
backend/sql/migrations/006_session_context.sql
```

保存时只保留小型结构化信息：

```json
{
  "active_station": {
    "station_id": "4",
    "name": "哲丰新材料九号机新增",
    "city": "衢州市",
    "lat": 28.941447,
    "lon": 118.525745,
    "capacity_kw": 300
  },
  "last_scope": {
    "type": "single"
  }
}
```

保存链路：

```text
用户选择站点
    ↓
context.last_user_selected_station
    ↓
Agent 任务成功完成
    ↓
chat.py finally 中读取上下文
    ↓
save_active_station()
    ↓
UPDATE chat_session.context_json
```

只有任务成功后才写入，避免失败任务把不完整或错误的选择写进会话状态。

### 3.6 第六阶段：下一轮通过 active_station 复用

新请求开始时：

```text
chat.py
    ↓
load_session_context(session_id, user_id)
    ↓
读取 context_json
    ↓
取出 active_station
    ↓
绑定到当前 StationResolutionContext
```

站点解析器对上下文指代词做了明确判断：

```python
_is_contextual_reference(reference)
```

目前支持：

```text
它
该站点
这个站点
刚才那个站点
刚才的站点
刚才那个
上一个站点
```

命中后直接返回：

```python
if context and context.active_station and _is_contextual_reference(reference):
    return _copy_station(context.active_station)
```

因此：

```text
上一轮：用户选择哲丰新材料九号机
下一轮：继续看看它今天的天气
        ↓
station_name = "它"
        ↓
命中 active_station
        ↓
直接使用 station_id=4
```

这不是让 Agent 自己“猜”出它指向谁，而是后端先读取结构化状态，再对有限的上下文指代进行安全映射。

## 4. 当前任务内缓存与会话级缓存的区别

| 层级 | 存储位置 | 生命周期 | 解决的问题 |
| --- | --- | --- | --- |
| 任务级缓存 | Python `ContextVar` | 一次 Agent 执行 | 防止同一任务重复询问和重复匹配 |
| 会话级缓存 | MySQL `chat_session.context_json` | 多轮会话 | 下一轮继续使用用户刚才确认的站点 |
| 数据库站点表 | MySQL `solar_station` | 长期 | 保存所有站点主数据 |

两层缓存不能互相替代：

```text
ContextVar 适合临时执行状态
MySQL       适合跨请求的持久状态
```

如果只使用 `ContextVar`，服务重启或下一轮请求后选择会消失；如果只使用 MySQL，每次工具调用都读取数据库，会增加访问次数，也无法自然绑定在当前异步执行上下文中。

## 5. 三种站点范围

### 5.1 单站点 `single`

```text
用户：预测英杰今天的发电量
```

流程：

```text
resolve_station("英杰")
    ├─ 唯一匹配：直接返回
    └─ 多个匹配：只询问这一项
```

### 5.2 明确多站点 `multi`

```text
用户：预测英杰和哲丰今天的发电量
```

流程：

```text
解析英杰
    → 唯一匹配

解析哲丰
    → 多个匹配
    → 只询问哲丰

最终得到多个结构化站点对象
```

不会因为哲丰存在歧义，就让用户重新选择英杰。

### 5.3 地区站点 `region`

```text
用户：看一下衢州地区所有站点今天的预测发电量
```

流程：

```text
提取关键词：衢州
    ↓
province/city/location/name LIKE '%衢州%'
    ↓
返回衢州地区全部有效站点
    ↓
不调用单站点 ask_user
```

地区查询入口：

```python
get_stations_by_region(region="衢州")
```

地区站点不再通过固定城市白名单判断，而是以 MySQL 中的真实数据为准。当前单次最多处理 20 个站点，查询 21 条用于判断是否超限。

## 7. 为什么不用全局字典保存 active_station

不能使用类似下面的模块级变量：

```python
active_station = {}
```

原因是：

1. 多个用户会互相覆盖；
2. 多个会话会互相污染；
3. 服务重启后丢失；
4. 多进程部署时每个进程各有一份状态；
5. 无法通过 `user_id + session_id` 做权限隔离。

现在的设计是：

```text
当前执行状态 → ContextVar
跨请求状态   → MySQL
```

Redis 未来可以作为热点缓存，但 MySQL 仍然适合作为会话结构化状态的来源之一；不能只把状态放在进程内存中。

## 8. 面试时的一分钟介绍

> 我在 SolarAgent 中把站点解析从工具内部的模糊字符串匹配，重构成了统一的结构化实体解析。用户输入“哲丰”时，系统会通过 `StationResolver` 匹配候选站点，必要时通过 `AskUserBridge` 暂停任务等待用户选择。选择结果会被转换成包含 `station_id`、标准名称、经纬度、装机容量和地区信息的结构化对象。一次 Agent 执行内，我使用 `ContextVar` 保存别名到站点对象的映射，避免天气、预测、图表等工具重复询问。任务成功后，再把用户明确确认的站点以 JSON 形式保存到 MySQL 的 `chat_session.context_json`。下一轮用户说“继续看看它的天气”时，后端会读取 `active_station` 并安全地解析“它”，而不是让大模型自行猜测。对于“宁波地区全部站点”这种集合意图，我又增加了 region 范围解析，直接按数据库的 province、city、location 模糊查询，不再误判为单站点歧义。

## 9. 面试追问与回答

### 问：为什么不用大模型记住用户选择？

答：对话历史适合保存自然语言上下文，但不适合作为业务实体的唯一来源。大模型可能忽略、改写或误解历史文本，所以我把关键业务事实结构化保存为 `station_id`、标准名称和经纬度。模型负责理解意图，后端负责事实绑定。

### 问：为什么要使用 `ContextVar`？

答：一次 Agent 执行可能包含多个异步工具调用，需要让这些工具共享同一个任务上下文。同时系统会并发处理多个用户和多个会话，模块级全局字典会导致数据串扰。`ContextVar` 可以把临时状态绑定到当前异步执行上下文，并在 `finally` 中清理。

### 问：为什么还要保存到 MySQL？

答：`ContextVar` 只对当前执行有效，下一次 HTTP 请求或服务重启后就不存在了。用户说“它”通常发生在下一轮请求，因此需要将小型结构化状态持久化到会话记录中。MySQL 保存来源事实，进程上下文只负责提高当前任务内的复用效率。

### 问：如果用户明确说了宁波地区，为什么不能继续用上一次选中的站点？

答：因为地区条件是新的范围指令，优先级高于上一轮单站点状态。只有“它”“刚才那个站点”这类上下文引用才会读取 `active_station`。明确地区、明确站点列表和当前任务解析结果都会覆盖历史提示。

### 问：地区查询为什么不让用户选择一个站点？

答：因为地区查询的语义是集合操作，不是单站点消歧。系统会按数据库中的地区字段返回站点集合，然后统一进行查询或预测。为了防止任务规模失控，目前设置了单次最多 20 个站点的上限。

### 问：模糊查询会不会查错地区？

答：地区查询只在用户明确表达地区范围时触发，并且查询条件限定在 `province`、`city`、`location` 和 `name` 字段。数据库返回的是候选集合，不会自动把多个站点压成一个站点。对于更严格的生产场景，还可以把地区标准化表和行政区编码引入查询层。

### 问：用户选择后任务失败，还会不会污染 active_station？

答：不会。当前任务先把选择放在 `last_user_selected_station` 中，只有 Agent 任务完整成功后，`chat.py` 才调用 `save_active_station()` 写入 MySQL。任务异常或取消时只清理当前 `ContextVar`。

### 问：如果用户选择了错误站点怎么办？

答：用户明确输入新的站点或重新选择后，会以新的确认结果覆盖 `active_station`。如果用户明确要求地区或多个站点，则不再使用之前的单站点提示。

## 11. 数据流示例：地区批量预测

```text
用户：看一下衢州地区所有站点今天的预测发电量
    ↓
识别 scope_type = region
    ↓
提取 region_keyword = 衢州
    ↓
SQL 查询 province/city/location/name LIKE '%衢州%'
    ↓
返回多个结构化站点
    ↓
检查数量是否超过 20
    ↓
逐个复用现有预测逻辑
    ↓
汇总结果或交给图表 DatasetArtifact 链路
```

这条链路不会调用：

```text
resolve_station("衢州")
    → 多匹配
    → ask_user 选择一个
```

因此集合意图和单站点歧义得到了隔离。

## 12. 已验证内容与运行注意事项

当前针对性测试覆盖：

```text
单站点任务级缓存
用户选择结果复用
跨轮 contextual reference
地区关键词清理
地区多站点结果保留
地区数量超限
工具注册
```

最近一次验证结果：

```text
7 passed
tool registration: ok
```

使用会话级 active_station 前，真实 MySQL 必须执行：

```powershell
mysql -u 用户名 -p solar_agent < backend/sql/migrations/006_session_context.sql
```

否则会出现：

```text
Unknown column 'context_json' in 'field list'
```

原因不是 Agent 失败，而是代码已经查询 `context_json`，数据库表结构还没有完成迁移。

## 13. 当前边界与后续方向

当前版本已经完成：

```text
站点文本 → 结构化站点对象
单次任务内复用
跨轮 active_station 复用
单站点 / 多站点 / 地区站点范围区分
地区模糊查询与数量限制
```

暂不引入：

```text
TaskPlan
复杂状态机
分布式任务队列
大规模并发预测调度
把全部历史站点列表永久塞入会话上下文
```

后续如果需要支持更长的地区批量任务，可以在当前结构化站点列表之上增加：

1. 批量任务进度记录；
2. 失败站点重试；
3. 并发数量控制；
4. 断点续跑；
5. Redis 热点缓存；
6. 行政区编码与标准地区表。

这些属于执行规模优化，不需要推翻当前的站点结构化解析设计。
