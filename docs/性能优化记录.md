# SolarAgent 性能优化记录

## 记录原则

每完成一项性能优化，使用同一组数据进行优化前后对比，记录：

- P50、P95 请求耗时；
- 数据库查询耗时；
- 返回消息条数和响应体大小；
- 数据库连接创建次数；
- 并发请求下的错误率。

提升百分比按以下公式计算：

```text
耗时提升率 = (优化前耗时 - 优化后耗时) / 优化前耗时 × 100%
```

在没有连接真实 MySQL 和执行压测前，不填写估算百分比。

## 第一阶段：统一 SQLAlchemy Engine

### 原问题

多个模块在每次查询时执行：

```python
engine = create_engine(MYSQL_URL)
...
engine.dispose()
```

这会导致连接池无法跨请求复用，增加 Engine 创建、连接初始化和销毁成本。

### 当前方案

新增 `backend/app/database.py`，提供进程级共享 Engine：

```text
首次访问数据库
    → 延迟创建 Engine
    → 创建连接池

后续请求
    → 复用同一个 Engine
    → 从连接池获取连接
    → with 代码块结束后归还连接

FastAPI 关闭
    → dispose_engine()
    → 释放连接池
```

已接入的模块包括：

- 会话路由；
- 图表快照存储；
- 发电量查询；
- 预测和气象缓存；
- 文件导入入库。

### 实测结果

2026-07-20 使用项目 `.env` 中的真实 MySQL，执行只读对照测试。两组测试均使用相同 SQL、相同用户和相同数据库，分别运行 60 次（3 轮 × 20 次），对比“每次请求创建并销毁 Engine”和“进程复用共享 Engine”。

| 场景 | 优化前平均 | 优化后平均 | 平均提升 | P50 提升 | P95 提升 |
|---|---:|---:|---:|---:|---:|
| 会话列表两条查询 | 14.41 ms | 1.84 ms | 87.23% | 92.48% | 94.39% |
| 单会话历史消息查询（42 条消息） | 14.60 ms | 1.57 ms | 89.23% | 94.07% | 95.82% |

测试只验证 Engine 和连接池开销，不能代表完整接口耗时。后续历史消息分页、联合索引和 Redis 缓存完成后，需要重新使用相同口径测量，避免把不同优化的收益混在一起。

## 第二阶段：历史消息分页加载

### 原问题

历史接口一次性读取整个会话的消息，并一次性读取该会话的全部图表快照。会话越长，数据库返回行数、JSON 解析量和前端首次渲染量越大。

### 当前方案

`GET /api/sessions/{session_id}/messages` 新增两个查询参数：

```text
limit：本次最多返回的消息数，默认 20，最大 200
before_id：只读取该消息 ID 之前的更早消息
```

接口按消息 ID 倒序取一页，再恢复为正序返回，并附带：

```json
{
  "has_more": true,
  "next_before_id": 723
}
```

前端首次进入会话只加载最近 20 条；用户点击“加载更早消息”时，携带 `next_before_id` 请求上一页，并通过滚动高度差保持阅读位置不跳动。图表快照查询同步按当前页的 `message_id` 过滤，同时兼容早期没有 `message_id` 的快照记录。

### 实测结果

2026-07-20 使用真实 MySQL、用户 4 的 42 条消息会话进行只读对比。两组使用同一连接池、同一会话、同一 SQL 语义，分别执行 60 次：

| 指标 | 优化前：全量读取 | 优化后：每页 20 条 | 提升 |
|---|---:|---:|---:|
| 消息返回行数 | 42 | 20 | 52.38% 减少 |
| 图表快照返回行数 | 6 | 3 | 50.00% 减少 |
| 平均数据库读取耗时 | 2.05 ms | 1.96 ms | 4.07% |
| P50 | 2.03 ms | 1.96 ms | 3.48% |
| P95 | 2.29 ms | 2.17 ms | 5.60% |

这里的耗时是接口核心数据库读取链路的只读基准，不是浏览器完整页面耗时。当前样本会话只有 42 条消息，因此数据库耗时下降有限；随着会话变长，分页对返回体大小、JSON 解析和前端渲染的收益会更明显。

## 第三阶段：Agent 记忆只读取最近窗口

### 原问题

`PersistentWindowSummaryMemory.load_memory_variables()` 原先通过 `self.chat_memory.messages` 查询整个会话，再在 Python 中截取最近 `2 * k` 条消息。会话越长，Agent 每轮推理都要读取和反序列化更多无关历史。

### 当前方案

数据库模式下使用 `_load_recent_messages(limit)`：

```text
message_store
    → 按 session_id、user_id 过滤
    → id 倒序 LIMIT 2*k
    → 恢复为时间正序
    → 使用原 converter 反序列化
```

当前运行环境统一使用 `SQLChatMessageHistory` 和共享 SQLAlchemy Engine，不再保留内存消息历史分支。这样 Agent 的上下文、摘要和原始消息都来自 MySQL，服务重启后行为一致。摘要生成会访问窗口之外的历史内容，因此在本阶段单独采用持久化游标方案处理。

### 实测结果

2026-07-20 使用真实 MySQL、用户 4 的 42 条消息会话进行只读对比，窗口大小为 `2 * k = 6`，两组各执行 60 次：

| 指标 | 优化前：读取全部消息 | 优化后：读取最近窗口 | 提升 |
|---|---:|---:|---:|
| 消息返回行数 | 42 | 6 | 85.71% 减少 |
| 平均读取耗时 | 3.25 ms | 1.94 ms | 40.13% |
| P50 | 3.22 ms | 1.93 ms | 39.99% |
| P95 | 3.59 ms | 2.20 ms | 38.74% |

该结果只测量 Agent 消息读取与反序列化，不包含 LLM 推理耗时。摘要读取仍是独立步骤，后续可单独优化。

## 第四阶段：Agent 记忆数据库访问统一连接池

### 原问题

Agent 记忆模块原先混用了两种数据库访问方式：最近窗口通过 LangChain 内部 ORM Session 读取，摘要读取、摘要写入和旧消息清理则直接调用 `pymysql.connect()`。这会造成数据库访问入口不统一，部分操作每次都重新建立底层连接。

### 当前方案

所有记忆相关 SQL 统一使用项目的共享 Engine：

```python
from backend.app.database import get_engine

with get_engine().connect() as conn:
    rows = conn.execute(text(sql), params).fetchall()
```

写入和删除统一使用事务：

```python
with get_engine().begin() as conn:
    conn.execute(text(sql), params)
```

本次覆盖：

- 最近窗口消息读取；
- 会话摘要读取；
- 会话摘要 UPSERT；
- 旧消息清理。

消息写入仍由 `SQLChatMessageHistory` 负责 LangChain 适配，但它绑定的是项目共享 Engine，底层连接同样来自统一连接池。

### 实测结果

2026-07-20 使用真实 MySQL、用户 4 的 42 条消息会话进行只读测试，各执行 60 次：

| 场景 | 优化前 | 优化后 | 平均提升 |
|---|---:|---:|---:|
| 最近窗口消息读取 | ORM 全量读取后截取，3.94 ms | 连接池直连 SQL，1.37 ms | 65.24% |
| 摘要读取 | 每次 `pymysql.connect()`，10.13 ms | 共享连接池，0.94 ms | 90.75% |

本次测试只读取真实 MySQL，没有执行写入、更新或删除操作。

## 第五阶段：摘要模块改为增量游标模式

### 原问题

旧实现只判断 `len(chat_memory.messages) > 2*k + summarize_threshold`。一旦会话超过阈值，这个条件会一直成立，导致每轮对话都可能再次调用摘要 LLM，并重复处理已经总结过的旧消息。

### 当前方案

`agent_summary_store` 新增三个持久化字段：

| 字段 | 作用 |
|---|---|
| `summary_until_message_id` | 摘要已经覆盖到的消息 ID 游标 |
| `summary_version` | 乐观并发控制版本，避免两个后台任务互相覆盖 |
| `source_message_count` | 最近一次摘要批次实际覆盖的原始消息条数 |

后台摘要每次执行以下流程：

```text
读取摘要状态和最近窗口边界
    → 统计游标之后、最近窗口之前的未摘要消息
    → 未达到 8 条：直接结束，不调用 LLM
    → 达到阈值：最多读取 16 条作为本次增量批次
    → LLM 将旧摘要与这批新消息整合
    → 按 summary_version + 游标条件提交
    → 并发冲突时丢弃过期结果，下一次重新读取最新状态
```

原始消息仍然保留在 `message_store`，摘要只是可重建的压缩视图；因此游标推进不会造成历史数据删除或不可恢复。

### 真实数据库验证

已将 `002_incremental_summary.sql` 应用到真实 MySQL，确认三个字段存在。使用真实会话做只读链路验证：最近窗口为 6 条，当前摘要游标为空时，检测到窗口外 36 条待处理消息，并正确截取首批 16 条；验证未调用真实 LLM，也未修改该会话摘要。

另外使用临时测试会话验证了提交与并发保护：首次提交成功、版本更新成功、使用旧版本的过期提交被拒绝，测试数据已清理。

### 后续收益

- 摘要 LLM 调用从“每轮可能调用”变为“每累计 8 条未摘要消息调用一次”；
- 每次只处理有限批次，单次延迟和 Token 成本可控；
- 服务重启后游标、版本和摘要仍在 MySQL 中，不依赖进程内计数器；
- 多 Worker/多实例并发执行时，乐观锁避免旧摘要覆盖新摘要。

## 第六阶段：会话列表按最后消息时间游标分页

### 原问题

会话列表原先一次性读取当前用户的全部会话，还要额外聚合 `message_store` 的最大消息时间，再由 Python 合并排序。会话数量增长后，返回体、数据库扫描和 Python 排序都会随总会话数增长。

### 当前方案

会话列表现在使用 `last_message_at` 作为主排序字段、`session_id` 作为同时间下的稳定次排序字段，并通过不透明游标继续加载下一页：

```text
第一页：ORDER BY last_message_at DESC, session_id DESC
下一页：last_message_at/session_id 之后的位置继续查询
```

新增索引：

```sql
(user_id, last_message_at, session_id)
```

前后端分页大小统一配置在 `shared/pagination.json`，当前会话列表每页 20 条，历史消息每页 4 条。

### 验证结果

真实 MySQL 验证了第一页和第二页游标往返：游标可正确解码，两页无重复会话；`EXPLAIN` 确认查询选择 `idx_chat_session_user_last_message` 索引。

### 游标分页的工程价值

游标分页也叫 Keyset Pagination，是大型列表系统常用的分页方式。它不依赖 `OFFSET` 跳过前面的大量数据，而是携带上一页最后一条记录的位置继续查询：

```text
第一页：ORDER BY last_message_at DESC, session_id DESC
下一页：从上一页最后的时间和 session_id 继续向后查
```

相比页码分页，它有几个优势：

- 数据量变大后，查询耗时不会随着页码线性增加；
- 新会话插入或旧会话更新时间变化时，不容易出现重复记录和漏记录；
- 适合消息、订单、日志、会话等持续变化的列表；
- 游标可以同时携带时间和唯一 ID，保证分页边界稳定。

### 联合索引是怎么使用的

本阶段新增：

```sql
CREATE INDEX idx_chat_session_user_last_message
ON chat_session (user_id, last_message_at, session_id);
```

应用代码不需要手动调用索引。MySQL 会根据查询条件和排序字段自动选择它：

```sql
WHERE user_id = :uid
ORDER BY last_message_at DESC, session_id DESC
LIMIT 21
```

索引的字段顺序对应查询过程：

```text
user_id：先定位当前用户的会话
    → last_message_at：按最后消息时间排序和定位游标
    → session_id：处理同一时间下的稳定排序
```

可以通过 `EXPLAIN` 查看是否使用：

```text
EXPLAIN_CHOSEN=idx_chat_session_user_last_message
```

### 真实 MySQL 性能对比

2026-07-20 使用真实 MySQL、用户 4 的实际会话数据，执行 60 次。旧方案包含“全量会话查询 + message_store 聚合 + Python 合并排序”；新方案包含“索引分页查询 + 总数查询”。

| 指标 | 优化前 | 优化后 | 平均提升 |
|---|---:|---:|---:|
| 平均数据库链路耗时 | 1.9215 ms | 1.4843 ms | 22.75% |
| P50 | 1.8732 ms | 1.4101 ms | 24.72% |
| P95 | 2.5330 ms | 1.7092 ms | 32.52% |
| 会话返回行数 | 6 + 6 聚合行 | 6 页数据 | 读取结构更简单 |

当前数据库只有 6 个会话，因此耗时差距还不大。会话数量扩大到几百、几千后，游标分页避免全量读取和 Python 排序的收益会更加明显。
