# 站点结构化解析与任务复用

## 1. 要解决的问题

用户通常会使用简称，例如“英杰”或“哲丰”。其中“哲丰”会匹配到多个真实站点。旧链路中，某个工具内部虽然已经让用户选中了站点，但后续预测工具又拿原始文本“哲丰”重新查库、重新模糊匹配，因此同一条任务可能连续询问两次。

本次改造的目标不是让模型“记住”一次选择，而是把选择结果变为可复用的结构化业务对象，并限定在当前任务内有效。

## 2. 当前实现总览

```text
用户输入：预测哲丰今天的发电量
        │
        ▼
chat.py 创建本任务的 StationResolutionContext
        │
        ▼
predict_power("哲丰", "今天")
        │
        ▼
StationResolver.resolve("哲丰")
  ├─ 缓存命中：直接返回结构化站点
  └─ 缓存未命中：查站点、处理歧义、必要时 ask_user
        │
        ▼
{
  station_id, name, lat, lon, capacity, location, ...
}
        │
        ▼
predict_station_power(full_name, station_id, lat, lon, ...)
        │
        ▼
预测、缓存、结果返回
```

核心原则：**下游代码传递的是站点对象，不再反复传递模糊文本名称。**

## 3. 源码分层与职责

| 文件 | 核心对象/函数 | 职责 |
| --- | --- | --- |
| `backend/app/routers/chat.py` | `bind_station_resolution_context()` | 每次 Agent 执行前创建独立任务上下文，结束后清理。 |
| `backend/app/services/station_resolver.py` | `StationResolutionContext` | 保存当前任务已解析的站点别名映射。 |
| `backend/app/services/station_resolver.py` | `StationResolver.resolve()` | 统一处理缓存、站点加载、模糊匹配、歧义选择与结果缓存。 |
| `backend/tools/weather_fetcher_tool.py` | `_match_station()` | 旧工具的兼容入口，内部委托给 `resolve_station()`。 |
| `backend/tools/pv_predictor.py` | `predict_power()` | 只解析一次站点，取出结构化字段后传给 `predict_station_power()`。 |

这样查询、天气、预测、图表、导出等工具都可以沿用同一个解析服务，而不会各自维护一套“简称匹配逻辑”。

## 4. 一次真实调用：以“预测哲丰今天的发电量”为例

### 4.1 路由创建任务级上下文

在 `chat.py` 的流式接口中，Agent 执行前会调用：

```python
station_context_token = bind_station_resolution_context()
```

它创建的是一个 `ContextVar` 中的 `StationResolutionContext`。这个上下文只属于本次用户消息，不是全局变量，也不写入数据库。

任务结束时，无论成功、异常还是取消，`finally` 都会执行：

```python
reset_station_resolution_context(station_context_token)
```

因此本次对“哲丰”的选择不会串到其他用户、其他会话或下一次新任务中。

### 4.2 `predict_power` 获取结构化站点

`pv_predictor.py` 中的 `predict_power()` 不再先调用文本式 `get_station_location`，然后重新用名称匹配。现在它执行：

```python
stations = _load_stations_from_db()
station_info = resolve_station(station_name, stations=stations)

lat = station_info["lat"]
lon = station_info["lon"]
station_id = station_info["station_id"]
full_name = station_info["name"]
```

此时 `station_info` 是一个 Python `dict`，典型字段包括：

```json
{
  "station_id": 4,
  "name": "哲丰新材料九号机新增",
  "lat": 28.941447,
  "lon": 118.525745,
  "capacity": 713.57,
  "location": "浙江省衢州市常山县..."
}
```

预测层随后使用 `full_name`、`station_id`、`lat`、`lon` 调用 `predict_station_power()`，不再把“哲丰”传回去重新解析。

### 4.3 `StationResolver.resolve` 的命中与选择逻辑

`resolve()` 的执行顺序如下：

```text
输入 "哲丰"
  │
  ├─ 规范化为缓存键："哲丰"
  │
  ├─ 本任务缓存有该键？
  │   ├─ 是：返回缓存副本，不再查库、不再提问
  │   └─ 否：继续
  │
  ├─ 获取站点集合（调用方传入则复用；否则从 MySQL 加载）
  ├─ `_match_all_stations("哲丰", stations)`
  │   ├─ 0 个：返回 None，由业务工具报“未找到站点”
  │   ├─ 1 个：直接选中
  │   └─ 多个：`request_user_input()` 展示候选序号，暂停任务
  │
  ├─ 缓存以下别名：原始输入、站点 ID、标准全名
  └─ 返回结构化站点对象副本
```

用户选择“2”后，解析器会同时记录：

```text
"哲丰"                 → 哲丰新材料九号机新增
"4"                    → 哲丰新材料九号机新增
"哲丰新材料九号机新增" → 哲丰新材料九号机新增
```

所以同一任务里，后续工具即使分别传入“哲丰”、`4` 或完整名称，都能拿到同一份站点对象。

## 5. 为什么使用 `ContextVar`

任务级缓存的边界必须严格：

```text
会话 A / 用户 1 / 本次任务：哲丰 → 九号机
会话 B / 用户 2 / 本次任务：哲丰 → 二车间
```

不能使用模块级 `dict`，否则并发请求可能相互污染。`ContextVar` 能把数据绑定在当前异步执行上下文中；`chat.py` 在 Agent 执行入口绑定，在 `finally` 清理，符合“任务内复用、任务间隔离”的要求。

它不是长期记忆：下一条用户消息重新解析是刻意设计，避免用户上一次选择的“哲丰九号机”在新的业务任务里被静默沿用。

## 6. 与 `ask_user` 的关系

站点歧义选择并没有让 Agent 通过自然语言自行反复发问，而是由 `StationResolver._choose_ambiguous_station()` 直接复用 `request_user_input()`：

```text
解析器发现多个候选
  → request_user_input(question)
  → 后端桥接到 SSE 的 user_input_required
  → Vue 展示 AskUser 卡片
  → 用户提交序号
  → 原任务恢复，返回选中的结构化站点
```

这与预测确认门共用同一套“暂停—回复—恢复”基础能力，但业务语义不同：

- 站点解析：确认“本任务操作哪个站点”。
- 预测确认门：确认“是否按指定站点、日期执行可能耗时的预测”。

## 7. 对后续模块的复用方式

以后任何需要站点信息的业务函数，不应自行写模糊匹配，而应使用：

```python
station = resolve_station(user_station_name)
```

然后向下游传递结构化字段，而不是继续传用户原始文本：

```text
查询实际电量   → station_id
预测发电量     → station_id + 经纬度 + 标准名称
获取图表数据   → station_id + 标准名称
导出文件       → station_id + 显示名称
```

如果同一任务需要查询英杰、哲丰、柯瑞，缓存会并存多组别名映射；它不是“只能存一个站点”的变量。

## 8. 当前边界与下一步

当前实现解决的是**单次 Agent 任务内**的确定性复用。它不替代长期记忆、会话摘要或数据库业务状态。

后续引入 `TaskPlan` 后，站点解析结果可作为计划的结构化输入：

```text
TaskPlan.resolved_stations
  └─ [ { station_id, name, lat, lon, ... } ]
```

届时：

- `StationResolver` 负责把模糊名称变成可靠对象；
- `TaskPlan` 负责保存“本任务要做什么、已解析到哪些实体、下一步是什么”；
- 执行器负责按计划调用预测、查询或图表服务。

因此 `StationResolver` 不会被 TaskPlan 淘汰，而是 TaskPlan 的实体解析基础设施。

## 9. 本次改造的验证点

已增加针对解析器的单元测试，覆盖：

1. 模糊名称在同一任务中只询问一次，随后命中缓存；
2. 新任务会重新询问，避免错误继承旧选择；
3. 唯一匹配站点不触发用户交互；
4. `predict_power` 直接使用已解析的结构化站点，不再调用文本式定位工具后二次匹配。
