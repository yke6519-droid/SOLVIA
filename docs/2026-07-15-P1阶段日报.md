## 一、今日结论

今天 P1 已从“静态页面原型”推进到“可承载真实业务交互的前后端基础闭环”：

- 独立 Vue 前端和 FastAPI 后端完成分离。
- 完成登录、JWT、登录态保存和未登录路由拦截。
- 完成会话列表、创建、切换、删除和历史消息恢复。
- 对话接入 SSE，前端可以边接收边展示 Agent 输出。
- Agent 输出按 Markdown 渲染，并经过 DOMPurify 安全过滤。
- 图表工具返回结构化 JSON，前端使用 ECharts 模板渲染。
- 支持单日逐小时图、多日逐小时图和多日按日汇总图。
- 图表结果写入数据库快照，历史会话重新打开时可恢复 ECharts。
- 对话流预留“理解任务 → 调用工具 → 整理结果 → 组织回答 → 完成”的过程轨迹。
- 深色/浅色工作台、登录页、确认卡片、图表卡片和对话布局完成多轮调整。

P1 的核心闭环是：

> 用户输入一个光伏运营问题，系统完成身份校验，进入会话，调用 Agent 与业务工具，返回流式 Markdown 和结构化图表，并把结果保存下来供后续复盘。

### 2.3 API 层：Axios 与 Fetch 按职责分工

| 业务 | 函数 | 底层 |
|---|---|---|
| 登录 | login | Axios |

~~~~mermaid
flowchart LR
    A[Vue 组件] --> B[业务 API 函数]
~~~~

### 2.5 SSE 流式对话和执行轨迹

接口：

~~~~text
POST /api/chat/stream
Content-Type: application/json
Accept: text/event-stream
Authorization: Bearer <JWT>
~~~~

事件协议：

| 事件 | 含义 | 前端处理 |
|---|---|---|
| token | LLM 增量文本 | 追加回答 |
| thinking / agent_step / step | Agent 阶段 | 更新过程轨迹 |
| tool_start | 工具开始 | 显示调用的工具 |
| tool_end | 工具结束 | 显示结果和图表数据 |
| user_input_required | 需要确认 | 展示问题和回复框 |
| error | 执行失败 | 标记错误 |
| done | 本轮完成 | 收尾并解除流式状态 |

~~~~mermaid
sequenceDiagram
    participant U as 用户
    participant V as Vue
    participant S as FastAPI SSE
    participant A as Agent
    participant T as 工具
    participant DB as MySQL

    U->>V: 输入查询、预测或可视化问题
    V->>S: POST /api/chat/stream
    S->>A: astream_events()
    A->>T: 查询、预测、图表
    T-->>S: tool_start / tool_end
    S-->>V: SSE 事件
    V-->>U: 流式显示过程与回答
    T-->>S: 结构化 chart_data
    S->>DB: 保存图表快照
    S-->>V: done
~~~~

前端通过 ReadableStream、TextDecoder 和缓冲区处理网络分包，以空行识别一个 SSE 事件。

## 三、今天踩过的坑

### 3.1 Vite 依赖缺失

现象：

~~~~text
Cannot find module frontend/node_modules/vite/bin/vite.js
~~~~

原因是 package.json 已声明 Vite，但 node_modules 不完整或依赖链接失效。这是依赖环境问题，不是 Vue 业务代码问题。

经验：先区分依赖错误和编译错误；package.json、lockfile、node_modules 必须一致；Windows 下依赖链接失效时，重新安装比修改业务代码更重要。

### 3.2 Uvicorn reload 扫描到 .pnpm-store

出现 esbuild 路径 FileNotFoundError，但同时有 Application startup complete。原因是 uvicorn reload 扫描了项目根目录，.pnpm-store 中的失效依赖路径被纳入扫描。异常影响 reloader，不等于 FastAPI 主服务没有启动。后续让 reload 只观察 backend，或开发时关闭 reload。

### 3.3 App.vue 乱码和模板结构损坏

根因是历史写入过程中编码不一致，导致中文乱码、引号截断和模板标签损坏。

~~~~mermaid
flowchart TD
    A[发现乱码] --> B[定位异常文本]
    B --> C{影响引号和标签?}
    C -- 否 --> D[替换异常字符串]
    C -- 是 --> E[保留逻辑并重建受损 template]
    D --> F[UTF-8 无 BOM 写回]
    E --> F
~~~~

经验：编码问题可能进一步演变成语法错误；PowerShell 写中文文件时统一 UTF-8 无 BOM；对受损 SFC 做局部替换前先判断结构是否可信。

### 3.4 历史图表不渲染

根因不是 ECharts，而是“快照没有挂回历史消息”：

~~~~text
数据库快照
  → 历史接口拼装 charts/chart_data
  → mapMessage()
  → message.chartData
  → PowerChart watch
  → setOption()
~~~~

需要从接口、状态映射、组件 props、生命周期四层一起排查。

### 3.5 切换会话闪过欢迎页

切换时先清空 messages，而模板把无消息直接判定为欢迎态。修复方式是增加历史加载态和请求序号校验。

### 3.6 深色模式卡片突兀

白色图表和米白卡片放在黑色背景上会割裂。现在改为主题变量、深色图表调色板、青绿色主操作色和统一边框文字对比度。

### 3.7 单日图表无法覆盖多日

原工具按 24 小时构建，无法表达 3 天和 10 天。现在增加日期范围工具、逐小时/按日聚合和 auto 粒度。

## 四、涉及的知识点

### 4.1 JWT 与路由守卫

~~~~mermaid
sequenceDiagram
    participant U as 用户
    participant F as 前端
    participant B as 后端
    participant DB as 用户表

    U->>F: 输入账号密码
    F->>B: POST /api/auth/login
    B->>DB: 查询和校验
    B-->>F: token + user + expires_in
    F->>F: 保存登录态
    F->>B: Bearer Token 请求
    B->>B: 解码 JWT 并注入 current_user
    B-->>F: 返回数据
~~~~

前端守卫改善体验，后端鉴权保证安全；localStorage 简单但有 XSS 风险，未来可评估 HttpOnly Cookie。

### 4.2 SSE 与事件协议

SSE 适合本项目：前端发送一次请求，后端持续推送多个事件，最后以 done 收尾。后端应把 LangChain 内部事件转换为业务事件，前端不直接依赖 LangChain 原始结构。

### 4.3 Markdown 安全渲染

~~~~text
Markdown 源文本
  → markdown-it
  → HTML
  → DOMPurify
  → DOM
~~~~

解析和安全清洗必须同时存在。

### 4.4 ECharts 模板化

~~~~mermaid
flowchart LR
    A[Agent 选择 chart_type] --> B[Agent 填充数据]
    B --> C[结构化 chart_data]
    C --> D[前端类型白名单]
    D --> E[ECharts 模板]
    E --> F[交互式图表]
~~~~

Agent 只负责选择类型和填数据，前端负责模板、样式、安全和交互。

### 4.5 Vue 生命周期和 ECharts

~~~~text
props 变化
  → watch
  → nextTick
  → setOption
  → ResizeObserver.resize
  → onBeforeUnmount.dispose
~~~~

历史恢复必须确保数据到达后重新 setOption。

### 4.6 数据库快照

图表快照是“可恢复的结果视图描述”，不是原始发电事实。原始事实来自业务表，快照用于避免历史会话打开时再次调用模型和工具。

## 八、今日复盘

### 产品思想

1. P1 不是“把页面做出来”，而是打通一个真实运营任务。
2. 闭环意味着从用户输入开始，经过系统判断、工具执行、结果呈现、历史保存，最后可以复盘。
3. 图表是运营判断的一部分，因此必须结构化、可交互、可恢复。
4. 先稳定主闭环，再扩展导入校验和复杂复盘，能避免范围失控。

### 架构思想

1. 前端、API、Agent、工具、数据库之间必须有稳定边界。
2. 前端不直接理解 LangChain 内部事件，后端提供业务事件协议。

## 十、流式显示问题复盘：为什么没有打字机效果

### 10.1 用户看到的现象

后端请求已经进入流式处理状态，前端也显示了“正在理解你的任务”，但 Agent 的正文没有随着 token 到达逐步出现，而是在整个任务完成后一次性显示。

这说明：

- 请求本身已经发出。
- SSE 连接没有立即失败。
- 前端的执行状态可以更新。
- 但回答正文的增量更新没有触发 Vue 的重新渲染。

### 10.2 根本原因

后端 SSE 和 Agent 流式链路本身已经存在：

- ChatOpenAI 配置了 streaming=True。
- AgentExecutor 使用 astream_events。
- 后端监听 on_chat_model_stream。
- 后端把模型增量内容转换成 token 事件。
- 前端 streamChat() 持续读取 SSE。

真正的问题出在 Vue 响应式对象的引用上。

原来的流程是：

~~~~text
创建普通 assistantMessage 对象
  → push 到 messages.value
  → SSE 回调继续修改原始 assistantMessage
  → Vue 没有追踪到这些修改
  → 页面保持“正在理解你的任务”
  → isStreaming 结束时触发一次整体更新
  → 用户看到完整回答
~~~~

也就是说，数据其实可能已经逐步追加到了 assistantMessage.content，只是这个对象不是当前 Vue 渲染树正在追踪的响应式代理对象。

### 10.3 解决方式

修复后的逻辑是：

1. 先把 assistantMessageData 放入响应式数组 messages.value。
2. 再从 messages.value 中取出最后一条助手消息。
3. SSE 回调统一修改这个响应式对象。
4. 每收到一个 token，message.content 变化都会触发 MarkdownMessage 重新渲染。

~~~~text
assistantMessageData
  → messages.value.push(...)
  → 从 messages.value 取出响应式 assistantMessage
  → token 到达
  → assistantMessage.content 追加文本
  → Vue 响应式更新
  → MarkdownMessage 重新渲染
  → 用户看到打字机效果
~~~~

本次修复只调整前端状态引用，没有改变后端接口、SSE 事件名称或图表协议。

### 10.4 为什么之前看起来像“后端没有流式输出”

这是一个容易误判的地方：

- 如果前端没有正确响应式更新，即使后端连续发送 token，页面也可能看起来没有变化。
- 等待状态变化、流式结束或其他响应式变量变化时，页面才会突然显示完整内容。
- 因此判断流式是否生效，不能只看页面是否逐字显示，还要分别检查：
  1. 后端是否产生多个 token 事件。
  2. 浏览器 Network 是否持续收到多个 SSE data。
  3. 前端 SSE parser 是否逐个触发 onEvent。
  4. Vue 是否正在修改响应式对象。
  5. Markdown 组件是否根据 content 变化重新渲染。

### 10.5 前后端交互图说明

本日报前面的“2.5 SSE 流式对话与执行轨迹”已经包含完整的前后端时序图，本次不重复绘制。

那张图表达的关键链路是：

~~~~text
用户输入
  → Vue 调用 streamChat()
  → POST /api/chat/stream
  → FastAPI 调用 Agent astream_events()
  → Agent 产生 token/tool_start/tool_end
  → FastAPI 转成 SSE 事件
  → Fetch ReadableStream 读取
  → onEvent 更新响应式消息
  → MarkdownMessage 和 PowerChart 渲染
  → done 结束本轮
~~~~

这次新增的重点，是把“token 已经到达”与“Vue 是否响应式重渲染”区分开来。

### 10.6 后续排查标准

如果后续仍然出现一次性显示，应按以下顺序排查：

| 层级 | 检查内容 |
|---|---|
| 模型层 | 模型服务是否真的返回增量 chunk |
| Agent 层 | astream_events 是否产生多个 on_chat_model_stream |
| FastAPI 层 | 是否逐个 yield token SSE |
| 代理层 | Nginx、网关或代理是否缓冲 SSE |
| 浏览器层 | Network 是否看到多个 event/data |
| API 层 | streamChat 是否逐个调用 onEvent |
| Vue 层 | 回调是否修改响应式对象 |
| 渲染层 | MarkdownMessage 是否根据 content 变化更新 |

## 十一、安全渲染详解：为什么必须清洗 Agent 输出

### 11.1 为什么 Agent 输出不能直接展示为 HTML

Agent 的回答本质上是外部输入，不能因为它“来自模型”就默认可信。

模型可能输出：

- 普通 Markdown。
- HTML 标签。
- 带链接的文本。
- 代码块。
- 用户输入中夹带的恶意内容。
- 工具结果中原样返回的数据库字段或文件内容。

如果前端直接这样写：

~~~~vue
<div v-html="message.content"></div>
~~~~

就等于把未经检查的字符串当成浏览器 HTML 执行。攻击者可能通过用户输入、导入文件、知识库内容或工具返回值注入：

~~~~html
<img src="x" onerror="窃取登录态">
<script>恶意脚本</script>
<a href="javascript:恶意代码">点击</a>
~~~~

这类问题属于 XSS（Cross-Site Scripting，跨站脚本攻击）。

### 11.2 SolarAgent 可能遇到的两类 XSS

#### 反射型 XSS

恶意内容随着当前请求返回，只影响当前页面。例如用户把恶意 HTML 放进问题中，Agent 又把它原样复述，前端直接注入页面就可能执行。

#### 存储型 XSS

恶意内容被保存到会话历史、数据库快照或知识库中，其他时间再次打开历史会话时执行。

SolarAgent 有历史消息、图表快照和文件读取能力，因此存储型 XSS 尤其需要注意：

~~~~mermaid
flowchart TD
    A[用户输入或文件内容] --> B[Agent / 工具原样返回]
    B --> C[保存到消息历史或快照]
    C --> D[历史会话再次打开]
    D --> E{是否直接 v-html?}
    E -- 是 --> F[恶意 HTML 进入浏览器]
    F --> G[XSS 风险]
    E -- 否 --> H[Markdown 解析与安全清洗]
    H --> I[只渲染允许的内容]
~~~~

### 11.3 当前项目的安全渲染链路

frontend/src/components/MarkdownMessage.vue 当前采用两步处理：

~~~~mermaid
flowchart LR
    A[Agent Markdown 原文] --> B[markdown-it 解析]
    B --> C[HTML 字符串]
    C --> D[DOMPurify.sanitize]
    D --> E[安全 HTML]
    E --> F[v-html 注入 DOM]
    F --> G[用户看到格式化回答]
~~~~

每一层的职责不同：

| 层级 | 工具 | 职责 |
|---|---|---|
| 解析 | markdown-it | 把标题、列表、表格、代码块转换成 HTML |
| 清洗 | DOMPurify | 删除危险标签、属性和协议 |
| 展示 | v-html | 只注入已经清洗过的 HTML |
| 样式 | styles.css | 控制排版，不执行用户内容 |
| 图表 | PowerChart | 根据结构化数据调用 ECharts，不执行模型 JavaScript |

### 11.4 markdown-it 做了什么

当前配置：

~~~~javascript
new MarkdownIt({
  html: false,
  linkify: true,
  breaks: true,
  typographer: false,
})
~~~~

#### html: false

禁止 Markdown 原文中的 HTML 直接作为 HTML 标签解析。例如：

~~~~markdown
<script>alert(1)</script>
~~~~

不会被当作脚本执行，而会被当作普通 Markdown 文本处理。

这是一道第一层防线，但不能替代 DOMPurify，因为：

- 未来配置可能发生变化。
- 其他组件可能继续使用 v-html。
- 工具结果和图表 tooltip 不是由 markdown-it 处理。
- 第三方插件或浏览器行为可能改变风险边界。

#### linkify: true

把普通 URL 自动转换成链接，提升可读性。它也会带来协议风险，因此后续仍需要 DOMPurify 检查 href 是否属于安全协议。

#### breaks: true

把换行转换为 HTML 换行，不涉及脚本执行。

### 11.5 DOMPurify 做了什么

当前调用包含：

~~~~javascript
DOMPurify.sanitize(html, {
  USE_PROFILES: { html: true },
  FORBID_TAGS: ['style', 'script', 'iframe', 'object', 'embed', 'form'],
  FORBID_ATTR: ['style', 'onerror', 'onclick', 'onload', 'onmouseover'],
  ALLOW_UNKNOWN_PROTOCOLS: false,
})
~~~~

具体含义：

- 只启用 HTML 清洗配置。
- 禁止 script，防止脚本执行。
- 禁止 iframe、object、embed，避免嵌入外部页面或插件内容。
- 禁止 form，避免伪造表单或诱导提交。
- 禁止 style，避免模型输出覆盖页面布局或注入 CSS。
- 禁止常见事件属性，如 onclick、onerror、onload、onmouseover。
- 不允许未知链接协议，降低 javascript:、data: 等危险链接风险。

清洗前：

~~~~html
<h3>预测结果</h3>
<img src="bad" onerror="窃取 token">
<a href="javascript:窃取登录态">查看详情</a>
<script>恶意代码</script>
~~~~

清洗后，正常标题可以保留，危险脚本、事件属性和危险协议会被移除。

### 11.6 为什么最后仍然使用 v-html

Vue 默认会把插值内容当作纯文本：

~~~~vue
<div>{{ message.content }}</div>
~~~~

这样是安全的，但 Markdown 不会渲染成标题、表格和列表。

因此需要：

1. 使用 markdown-it 把 Markdown 转换成 HTML。
2. 使用 DOMPurify 清洗 HTML。
3. 只把清洗后的结果交给 v-html。

安全边界不是“禁止 v-html”，而是：

> v-html 只能接收经过明确清洗、来源可追踪、协议受限的 HTML。

### 11.7 图表 tooltip 也需要安全处理

Markdown 安全并不覆盖 ECharts tooltip。

PowerChart.vue 中，图表标题、系列名称、坐标轴标签和单位也可能来自工具数据，因此组件额外使用 escapeHtml：

~~~~javascript
function escapeHtml(value) {
  return String(value ?? '')
    .replaceAll('&', '&amp;')
    .replaceAll('<', '&lt;')
    .replaceAll('>', '&gt;')
    .replaceAll('"', '&quot;')
    .replaceAll("'", '&#039;')
}
~~~~

tooltip 生成 HTML 时：

- 先把站点名、系列名、时间标签、单位转义。
- 只允许数值按照格式化函数输出。
- 不接受 Agent 返回的 ECharts JavaScript。
- 不把 chart_data 当成可执行配置代码。

这体现了两条独立的安全链路：

~~~~text
Agent Markdown
  → markdown-it
  → DOMPurify
  → v-html

结构化 chart_data
  → 字段校验
  → 数值格式化
  → escapeHtml
  → ECharts tooltip
~~~~

### 11.8 为什么前端清洗不是唯一安全措施

前端清洗是最后一道展示层防线，不应该替代后端安全：

- 后端仍应校验用户身份和会话归属。
- 工具返回的数据应限制字段和长度。
- 文件导入内容不应直接当作可信 HTML。
- 数据库快照需要限制大小和结构。
- 后端日志不能记录完整 token。
- 生产环境应配置 CSP（Content Security Policy）。
- 服务器应限制 iframe、对象嵌入和不必要的外部资源。
- 重要操作仍需要 ask_user 或业务确认。

完整的纵深防御：

~~~~mermaid
flowchart TD
    A[用户输入] --> B[身份认证]
    B --> C[会话归属校验]
    C --> D[工具参数校验]
    D --> E[Agent 输出约束]
    E --> F[Markdown 解析]
    F --> G[DOMPurify 清洗]
    G --> H[文本和 tooltip 转义]
    H --> I[CSP 与浏览器安全策略]
    I --> J[最终展示]
~~~~

### 11.9 流式输出中的安全处理

流式输出不是“先显示、最后再清洗”。正确方式是：

- 每次 token 更新原始 Markdown。
- MarkdownMessage 重新解析当前内容。
- 当前内容每次都经过 DOMPurify。
- 未闭合的代码块、链接或表格只作为临时内容渲染。
- 不执行任何模型返回的 JavaScript。
- 任务完成后也不跳过清洗步骤。

~~~~text
token 1
  → 部分 Markdown
  → 解析
  → 清洗
  → 展示

token 2
  → 更新后的 Markdown
  → 再次解析
  → 再次清洗
  → 更新展示
~~~~

### 11.10 当前方案的边界

当前方案解决了主要的 XSS 展示风险，但仍需要持续关注：

- linkify 生成的外部链接是否需要统一增加 rel="noopener noreferrer"。
- 是否允许 Markdown 中的图片。
- 是否需要禁止所有外链图片，避免隐私泄露和追踪像素。
- 是否需要配置更严格的 CSP。
- 是否需要限制单条消息最大长度，防止超大 Markdown 造成前端卡顿。
- 是否需要对代码块增加复制按钮时避免把未清洗内容写入 DOM。
- 是否需要在后端建立统一的输出 schema，减少任意字段进入前端。

安全渲染的最终原则：

> Agent 可以生成内容，但不能获得浏览器执行权；前端可以渲染格式，但只能渲染经过解析、清洗、转义和白名单校验的内容。
